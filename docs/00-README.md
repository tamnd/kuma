# kuma

A dataframe engine for Go. Columnar, lazy, vectorized, and typed at compile time.

`github.com/tamnd/kuma`

Written 25 August 2026, against Go 1.27, pandas 3.0 and Polars 1.43.

## What this is

pandas, for people who would rather write Go. Not a wrapper around Python, not a binding to something written in Rust, and not a toy. A complete columnar query engine with an Arrow memory layout, a lazy expression API with a real optimizer, parallel execution, hand vectorized kernels, and column names that the compiler checks.

The one line pitch is that it is the first dataframe library where a typo in a column name is a compile error.

## What this is not

It is not a database, so there is no storage engine, no transactions and no server.

It is not a machine learning library. Hand the frame to something else through Arrow.

It is not finished, and these documents describe roughly 62 person weeks of engine work plus 15 of bindings before there is a defensible 1.0. Document 08 says where the decision points are.

## The decisions already made

Everything below is settled. Where a decision has a cost, the cost is named.

**Typed columns are the default and strings are the escape hatch.** Generated by `kumagen` from a Go struct, or from a Parquet file, a CSV sample or a SQL table. Costs a code generation step. Buys compile time checking, autocomplete, jump to definition and safe renames. Document 03.

**Go 1.27 generic methods are load bearing from M3.** `Agg[R]` and `Select[R]` are methods that introduce a type parameter the receiver does not have, and before 1.27 they were impossible. This is why the project is worth starting now and not two years ago. It also means the language feature underneath the API is one release old, which is the largest single risk in the plan.

**Arrow layout, our own kernels.** The layout buys zero copy interop with everything. arrow-go's compute is thin enough that building on it would block us constantly, and the kernels are what we exist to provide. Document 01, section 4.

**StringView is the default string representation.** A 16 byte view with an inline prefix, so most comparisons never touch the heap. arrow-go's support for it is thin, which makes it a place a Go engine can lead.

**SIMD is an optimization and never a dependency.** The library builds, tests and works correctly on stock Go 1.27 with no experiment flag. Every vectorized kernel has a scalar twin, and the twin is the specification. Document 05.

**No `internal/` directory.** This was a requirement. It is paid for with aggressive unexporting, documented stability tiers and a low package count. The upside is that `kuma/bitmap` and `kuma/kernel` are usable on their own. Document 11.

**Every pandas feature is covered, in Go idiomatic form.** Document 06 is a tickable checklist of the entire pandas surface. There are exactly five genuine omissions and each one is listed with what to use instead.

**No automatic index alignment.** An index is optional and explicit. When you set one you get `loc`, `reindex`, `align` and the rest. What never happens is two frames silently aligning during arithmetic, which is the actual footgun rather than the index itself.

**Four repositories.** `kuma` for the library, `kuma-py` and `kuma-js` for the bindings, `kuma-bench` for the benchmarks. Separate because the dependency sets are incompatible and the release cadences differ.

**Benchmarks run from M1, continuously, and we publish the ones we lose.** A suite that only reports wins is an advertisement. Document 10.

## Prerequisites

Go 1.27 or newer. Check with `go version`, since anything older will not compile the typed API at all. As of this writing the machine this was drafted on runs 1.26.7, so upgrading is step zero.

`GOEXPERIMENT=simd` for the vectorized path, and nothing at all for the scalar path. Both are supported configurations and both are tested.

For `kuma-bench` and the conformance suite: Docker, Python 3.13 or newer, pandas 3.0, Polars 1.43 and DuckDB. None of this is needed to build or test the Go library, which is the entire reason those live in other repositories.

## A note on the name

`kuma` is 熊, bear. It follows the pandas and Polars lineage without being a pun about it.

There is a collision worth knowing about. `kumahq/kuma` is the Kong service mesh, and it is well known in its own corner of the world. It is not a Go dataframe library and nobody is going to confuse the two in context, and `github.com/tamnd/kuma` is unambiguous as an import path. It does mean that searching for "kuma go" alone will find the mesh first, so documentation and release notes should say "kuma dataframe" where the context is not already obvious.

The name is also the cheapest thing in this entire specification to change later, so it is not worth more thought than this paragraph.

## Honesty about scope

These documents describe a large project. The parts that are genuinely hard are the optimizer at M3, the parallel executor at M4, and streaming at M9, and each of those is where the estimates are least trustworthy.

The parts that look hard and are not include most of M7, which is volume rather than difficulty and parallelizes across contributors, and the bindings track, which is mostly careful plumbing over a boundary that document 07 deliberately keeps narrow.

The part most likely to be wrong is the assumption that Go 1.27's generic methods behave well enough at scale to carry the API. That is why M1 exists in the shape it does: to find out while it is still cheap.

The three checkpoints where stopping is a reasonable answer are after M2, after M4 and after M7, and document 08 says what question each one asks.
