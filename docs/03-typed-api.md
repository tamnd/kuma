# Typed columns and code generation

## The problem with string column names

Every dataframe library in every language identifies columns by string. `df["price"]`, `pl.col("price")`, `kuma.Col("price")`. It is the obvious design and it is what everyone copies.

It is also the single biggest source of avoidable pain in day to day data work. A typo in a column name is a runtime error, and in a long pipeline it is a runtime error that shows up ten seconds into a job rather than at the point you wrote it. Renaming a column means grepping for a string literal and hoping. There is no autocomplete, no jump to definition, no find all references. The compiler, which is the main reason to be writing Go at all, sits the whole thing out.

Python has an excuse: there is no compile step to check anything at. Go does not have that excuse. If we ship a stringly typed API we have built a slower pandas with worse ergonomics, and there is no reason for anyone to use it.

So the default in kuma is typed column handles, generated from your schema. Strings remain available for genuinely dynamic work, but they are the opt out rather than the normal path.

## What it looks like

You write a struct describing your data, the same way you would for `encoding/json`:

```go
//go:generate kumagen -type Trade

type Trade struct {
    Symbol string    `kuma:"symbol"`
    Price  float64   `kuma:"price"`
    Qty    int64     `kuma:"qty"`
    Side   string    `kuma:"side"`
    TS     time.Time `kuma:"ts"`
}
```

`kumagen` writes a file next to it containing one variable:

```go
// Code generated by kumagen. DO NOT EDIT.

var TradeCols = struct {
    Symbol kuma.StrCol[Trade]
    Price  kuma.F64Col[Trade]
    Qty    kuma.I64Col[Trade]
    Side   kuma.StrCol[Trade]
    TS     kuma.TimeCol[Trade]
}{
    Symbol: kuma.NewStrCol[Trade]("symbol"),
    Price:  kuma.NewF64Col[Trade]("price"),
    Qty:    kuma.NewI64Col[Trade]("qty"),
    Side:   kuma.NewStrCol[Trade]("side"),
    TS:     kuma.NewTimeCol[Trade]("ts"),
}
```

And then queries are ordinary Go expressions over ordinary Go values:

```go
t := TradeCols

out, err := kuma.ScanParquet[Trade]("trades/*.parquet").
    Filter(t.Price.Gt(100).And(t.Side.Eq("BUY"))).
    GroupBy(t.Symbol, t.TS.Trunc(time.Minute)).
    Agg[Bar](
        t.Price.Mul(t.Qty).Sum().To(BarCols.Volume),
        t.Price.Quantile(0.99).To(BarCols.P99),
        kuma.Count().To(BarCols.N),
    ).
    SortDesc(BarCols.Volume).
    Head(20).
    Rows(ctx)
```

`out` is a `[]Bar`. Not a bag of `any`, not a map, not something you have to assert your way out of.

The things that now fail at compile time rather than at runtime:

- `t.Prive.Gt(100)` does not compile, because there is no field called `Prive`.
- `t.Side.Gt(100)` does not compile, because `StrCol` has no `Gt(float64)`.
- `t.Price.Contains("x")` does not compile, because `F64Col` has no `Contains`.
- `t.Price.Sum().To(BarCols.Symbol)` does not compile, because you cannot write a float64 aggregate into a string column.
- Using `TradeCols.Price` against a `LazyFrame[Order]` does not compile, because the column handle carries the schema type it belongs to.

Renaming a column is now a rename in the struct, `go generate`, and the compiler tells you every place that needs updating.

## How the types fit together

Three families of type, all concrete structs. They have to be concrete: Go 1.27 allows generic methods only on concrete types, never on interfaces, so the moment any of these became an interface we would lose the ability to write methods like `Agg[R]` that change the schema.

**Column handles** name a column and remember which schema it came from and what type it holds.

```go
type F64Col[S any]  struct{ ref colRef }
type I64Col[S any]  struct{ ref colRef }
type StrCol[S any]  struct{ ref colRef }
type BoolCol[S any] struct{ ref colRef }
type TimeCol[S any] struct{ ref colRef }
```

They are separate named types rather than one generic `Col[S, T]` because the method sets genuinely differ. `Contains` belongs on strings, `Sum` belongs on numbers, `Trunc` belongs on timestamps. Go cannot make a method conditional on a type parameter, so distinct types are the only way to get the method set right. These are generated once inside the library, not once per user.

**Expressions** are what you get when you do something to a column.

```go
type F64Expr[S any]  struct{ n *node }
type StrExpr[S any]  struct{ n *node }
type BoolExpr[S any] struct{ n *node }
```

`t.Price.Gt(100)` is a `BoolExpr[Trade]`. `t.Price.Mul(2)` is a `F64Expr[Trade]`, and the same operation against another column is `t.Price.MulExpr(t.Qty.AsF64())`. The two spellings exist because a value written in the query and a second column are different arguments, and one method taking both would have to take `any` and give the type checking away. A handle and an expression of the same type share a method set through a small interface, `F64Value[S]` and its four siblings, so anything that takes one takes the other.

Combining expressions from two different schemas is a compile error, which is what stops the classic mistake of filtering the trades frame with a predicate you wrote against the orders frame.

**Frames** carry their schema as a type parameter.

```go
type LazyFrame[S any] struct{ plan *plan.Node }
type Frame[S any]     struct{ cols []column }
```

`Filter` takes a `BoolExpr[S]` and gives back a `LazyFrame[S]`. Operations that change the shape of the data take a new schema type, and this is exactly where Go 1.27 earns its place in the design:

```go
func (lf *LazyFrame[S]) Select[R any](cols ...Expr[S]) *LazyFrame[R]
func (lf *LazyFrame[S]) Agg[R any](aggs ...Agg[S]) *LazyFrame[R]
func (lf *LazyFrame[S]) Join[R, Out any](other *LazyFrame[R], on JoinKeys[S, R]) *LazyFrame[Out]
func (lf *LazyFrame[S]) Rows(ctx context.Context) ([]S, error)
```

Before Go 1.27 a method could only use the type parameters of its receiver, so `Agg[R]` was impossible. You had to write `kuma.Agg[Trade, Bar](lf, ...)` as a free function, which breaks the chain and reads terribly. That single restriction is why nobody has built this API in Go before, and it is why this project is worth starting now rather than two years ago.

## Where the names get checked against real data

There are three places a column name can be wrong, and the design catches them at three different times.

The name in the Go struct tag is checked against the file schema when you scan. That check happens once, at plan time, before any data is read, and it produces a proper error listing what the file actually contains. This is the same check the dynamic API does.

The name in your query is checked by the compiler, because it is a field selector on a generated struct rather than a string.

The struct itself can be checked against a real file at generate time, which closes the loop. `kumagen` can read the schema out of a Parquet file, a CSV sample, an Arrow IPC file, or a SQL table, and write the Go struct for you:

```
kumagen -parquet trades/2026-08-01.parquet -type Trade -o trade_kuma.go
kumagen -csv sample.csv -type Trade -o trade_kuma.go
kumagen -sql "postgres://..." -table trades -type Trade -o trade_kuma.go
```

Now the Go struct is derived from the data rather than typed out by hand, and the only way to get a name wrong is for the data itself to change. Running `kumagen` in CI against a reference file turns a schema change upstream into a failing build, which is roughly a thousand times better than finding out in production.

## The generator

`kumagen` is a small program with no cleverness in it. It is not a framework and it does not need to understand your query.

Given a Go struct it emits the `Cols` variable, a `Schema()` method, and the field to column index mapping used by `Rows`. Given a data file it emits the struct too. It handles nested structs by flattening with a dotted prefix, and slices by mapping to the Arrow list type. Unexported fields are skipped. A field with no `kuma` tag uses a snake_cased version of the field name, following the same convention as most Go JSON code.

It writes one file per type, named `<type>_kuma.go`, with the standard generated file header so that linters and diff tools leave it alone. The output is plain readable Go that you can open and understand, not a wall of reflection.

Two properties matter more than any feature it might have. It must be fast enough to run on every build without anyone noticing, and its output must be deterministic so that regenerating produces a byte identical file when nothing changed. Both are easy if the tool stays boring.

## What cannot be typed, and what to do about it

Being honest about the limits is more useful than pretending there are none.

Some operations produce columns whose names come from the data rather than the code. A pivot on `symbol` produces one column per distinct symbol, and no type system can know those in advance. Same for reading a CSV whose header you have never seen, or a `SELECT *` against a table that changed last week.

For all of these there is a dynamic path that works exactly like every other dataframe library:

```go
lf := kuma.ScanCSV[kuma.Dynamic]("unknown.csv")
lf = lf.FilterDyn(kuma.Dyn("price").Gt(100))
f, err := lf.Collect(ctx)
```

`kuma.Dynamic` is the schema type meaning "not known at compile time". Everything on a `LazyFrame[Dynamic]` takes strings and is checked at plan time. The naming is deliberately a little clumsy so that reaching for it is a visible choice rather than an accident.

The bridge back is `Bind`, which checks a dynamic frame against a struct once and hands you a typed frame:

```go
typed, err := kuma.Bind[Trade](f)
```

After that call you are back in the checked world. In practice the shape of most real programs is a short dynamic prologue that reads whatever arrived, a `Bind`, and then a long typed body.

## Two levels of strictness

The schema type parameter on column handles is the strict version. It catches using a column against the wrong frame, which is a real mistake people make, but it does mean every helper function you write has to name the schema type.

There is a lighter variant where column handles carry only their value type:

```go
var price = kuma.F64("price")   // F64Col, not F64Col[Trade]
```

You still cannot call `Contains` on a float or compare a string to a number, and the name is still written exactly once instead of scattered through the code. What you lose is the cross frame check, which moves from compile time to plan time.

The recommendation is to use the strict version for generated code, because the extra type parameter lives in a file nobody reads, and to leave the light version available for hand written helpers and quick scripts. Both compile down to the same plan, so mixing them within a program is fine.

## Cost

The typed layer builds the same expression nodes the dynamic layer does. `t.Price.Gt(100)` allocates one node, exactly as `kuma.Col("price").Gt(100)` would. The column handle is two words and never escapes. There is no reflection on the query path at all, only in `Rows` and `FromStructs` where it is unavoidable, and even there the field mapping is computed once per type and cached.

The milestone exit criterion for the typed layer is that it comes within five percent of the dynamic path on the benchmark suite. If it costs more than that, something is wrong with the implementation rather than with the design, because it is a facade over identical machinery.

Generic methods are invisible to reflection in Go 1.27, so nothing in this design may depend on enumerating methods at runtime. The reflection we do use looks at the schema struct, which is an ordinary type and reflects normally.

## Why this is worth the code generation step

Go programmers are reasonably suspicious of code generation. It adds a build step, it puts files in your repo that you did not write, and when it goes wrong it goes wrong confusingly.

The trade here is favourable for three reasons. The generated code is small, maybe fifteen lines per struct, and completely readable. The generator has no runtime component, so nothing can go wrong at execution time that was not already visible at build time. And the alternative is not "no generation", it is "string literals everywhere and hope", which is what every other dataframe library offers and which is precisely the thing Go is supposed to save you from.

You can also skip the generator entirely and write the `Cols` variable by hand. It is fifteen lines. The generator exists to keep it in sync with the data, not because the pattern requires tooling.
